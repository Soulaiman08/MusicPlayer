## 1. إعادة إنتاج الملاحظة البصرية للاختناق عند Maximized

### 1.1 ما ورد من المستخدم (مدخل التحقيق، وليس فرضية)
> عند تكبير النافذة يصبح التمرير مختنقاً وأقل سلاسة؛ حركة غير طبيعية، ولحظات تقطيع وثقل أثناء التنقل داخل القوائم والشبكات.

### 1.2 ما أستطيع تأكيده
لا أستطيع تأكيد أو نفي هذه الملاحظة بصرياً: أنا أعمل عبر أوامر نصية ولا أملك واجهة تفاعلية أُحرّك فيها عجلة الفأرة وأُلاحظ الإحساس بالحركة. **غياب التقطيع في أي أداة قياس لا يُعدّ نفياً للملاحظة البصرية** — وهذا مذكور صراحةً في تكليف M2.5.

### 1.3 ما أُنجز بدلاً من ذلك
تحققت من أن الأدوات التي أنتجت أرقام التقرير السابق **غير صالحة لإثبات الإطارات المعروضة** (انظر القسم 3)، أي أن غياب التقطيع في تلك الأرقام لا يمكن استخدامه للطعن في ملاحظة المستخدم.

### 1.4 بروتوكول إعادة الإنتاج المطلوب (لتنفيذه في جلسة تفاعلية)
لكل من: صغيرة / متوسطة / مكبرة، ولكل من: `fixture201` و `fixture5000`:

1. فتح التبويب المطلوب والتأكد من تفعيله عبر UIA **قبل** القياس (انظر مشكلة `Invoked=False` في القسم 3.أ).
2. Slow / Medium / Fast / تمرير مستمر 30 ثانية / الوصول للنهاية والعودة.
3. Cold و Warm، و5 تكرارات لكل حالة مع تغيير ترتيب التشغيل.
4. تسجيل شاشة متزامن مع طابع زمني مشترك مع السجل.
5. مقارنة الإحساس البصري مع PresentMon/ETW — **وليس مع `CompositionTarget.Rendering`**.

**التوثيق المتاح في هذه الجلسة:** لا يوجد تسجيل فيديو ولا لقطات جديدة. أُضيف هذا صراحةً كفجوة وليس كنتيجة.

## 3. مراجعة موثوقية أرقام التقرير السابق

### أ. قيم CPU Time (718.8ms / 125.0ms وغيرها)

**المصدر المُثبت:** `tools/perf/RunGlobalAuditSuite.ps1`، الأسطر 222–248:

```powershell
$cpu0 = $proc.TotalProcessorTime.TotalMilliseconds
Do-Scroll $musicHwnd 6 180      # Slow
$cpu1 = $proc.TotalProcessorTime.TotalMilliseconds
Do-Scroll $musicHwnd 25 35      # Fast
$cpu2 = $proc.TotalProcessorTime.TotalMilliseconds
CpuSlowMs = $cpu1 - $cpu0
CpuFastMs = $cpu2 - $cpu1
```

| سؤال التكليف | الإجابة المُتحققة | الأثر |
| :--- | :--- | :--- |
| CPU Time أم Wall Clock؟ | **`TotalProcessorTime`** = مجموع زمن المعالج لكل خيوط العملية، ليس Wall Clock، وليس UI Thread فقط | لا يمكن تفسيره كزمن حظر UI Thread |
| هل جُمعت أزمنة عدة عمليات؟ | نعم، **كل خيوط العملية** (ThreadPool، مُصوّر الصور، الزجاج، إلخ) | لا يُعزى إلى التمرير وحده |
| ما مدة الاختبار؟ | `Do-Scroll` ينتهي بـ `Start-Sleep 2200ms` ثابت (السطر 104). Slow ≈ 6×180ms + 150ms + 2200ms ≈ **3.43s**؛ Fast ≈ 25×35ms + 150ms + 2200ms ≈ **3.23s** | نافذتا قياس مختلفتان الطول |
| كم حدث تمرير؟ | Slow = 6، Fast = 25 | **مقارنة مباشرة بين Grid وList غير صالحة** بنفس القدر |
| هل القياس خاص بـ UI Thread؟ | ❌ لا | ❌ |
| ماذا تعني `0.0 ms`؟ | دقة `TotalProcessorTime` على Windows ≈ 15.6ms. كل القيم في CSV مضاعفات 15.625 (15.6 / 31.2 / 125.0 / 718.8 = 8×15.625 ... إلخ). `0.0` يعني **أقل من دقة المؤقت**، أي استهلاك يقترب من الصفر خلال النافذة | ❌ **تسمية `(Saturated)` في التقرير السابق خاطئة** — التشبع لا يُنتج صفراً |
| هل تُنسَب القيم إلى التبويب الصحيح؟ | ❌ **معظم الصفوف `Invoked=False`** في `perf-results/global-audit/current-f201-suite-summary.csv` (16 من 20). أداة UIA لم تُفعّل التبويب، فقيس whatever كان معروضاً | ❌ جدول «التبويب / الصفحة» في التقرير السابق **غير موثوق الإسناد** |

**خلاصة القسم أ:** الرقمان 718.8ms و125.0ms موجودان في الملف فعلاً، لكنهما **زمن معالج لكل العملية خلال ~3.2–3.4 ثانية تشمل 2.2 ثانية سكون**، بإسناد تبويب غير مؤكد. لا يجوز استخدامهما كـ «تكلفة AncestorType» ولا كدليل مقارن بين Grid وList.

## 4. الاختبار الأول: Window Composition و DWM

### 4.1 الفرضية كما وردت
«شفافية النافذة و WindowChrome قد تزيد تكلفة العرض، خصوصاً في النافذة المكبرة».

### 4.2 ما تحققت منه فعلياً
- `WS_EX_LAYERED = False`, `WS_EX_COMPOSITED = False` → **النافذة ليست Alpha-Layered**.
- `WindowStyle = SingleBorderWindow` → **ليست نافذة بلا حدود** كما ادعى التقرير السابق.
- `AllowsTransparency` غير مضبوط على Window → لا مسار `UpdateLayeredWindow`.
- `Background="Transparent"` على Window و RootBorder موجود فعلاً.
- `GlassFrameThickness = 0,32,0,0` و `CaptionHeight = 32` موجودان فعلاً.

### 4.3 الحكم
- ❌ **ادعاء التقرير السابق «النافذة شفافة بالكامل / Alpha Layered / بلا حدود صلبة» مُفند فعلياً** بالقيم أعلاه.
- ⚠️ يبقى احتمال أن لون clear الشفاف (`Transparent`) يفرض خلط alpha عبر DWM حتى مع عدم كون النافذة Layered — لكن **لم أُثبت هذا بالقياس**، ولا أملك PresentMon لقياس Present Time.
- ❌ **لم أنفّذ A/B** (RootBorder معتم مع الإبقاء على WindowChrome وبقية التصميم). لا توجد أرقام Frame Time / GPU 3D Engine / UI CPU لهذه التجربة.
- وفقاً لتعليماتك: **لا أعتبر غياب A/B دليلاً نهائياً، ولم أطبّق الخلفية المعتمة كتغيير دائم.**

### 4.4 ما يلزم لإتمام هذا الاختبار
بناء متغير مؤقت (RootBorder معتم فقط، بعزل هذا المتغير)، تشغيل نفس بروتوكول التمرير في small / medium / max مع PresentMon أو ETW، ثم مقارنة Present Time و GPU 3D Engine (مع التمييز بين GPU General و GPU 3D Engine الخاص بعملية MusicPlayer).

## 6. الاختبار الثالث: CircleClipConverter

### 6.1 الكود الفعلي (`Converters.cs:579–611`)

```csharp
// CircleClipConverter — square item width → one shared, frozen circular clip.
private static readonly ConcurrentDictionary<double, EllipseGeometry> Cache = new();

return Cache.GetOrAdd(width, static w => {
    double r = w / 2.0;
    var geometry = new EllipseGeometry(new Point(r, r), r, r);
    geometry.Freeze();
    return geometry;
});
```

### 6.2 الحكم
- ❌ **ادعاء التقرير السابق («StreamGeometry غير مجمدة تُنشأ في كل استدعاء لكل بطاقة») مُفند فعلياً.** الكود الحالي يستخدم `EllipseGeometry` **مجمدة ومخزنة مؤقتاً لكل عرض مختلف**، مشتركة بين كل البطاقات.
- أُضيفت هذه الآلية في commit `f8d2502` (مع VirtualizingBalancedPanel)، أي أنها موجودة قبل التقرير السابق.
- استخدامات المحول: سطران فقط (1243 و1797) في `MainWindow.xaml`، كلاهما على `Clip`.
- عينات محفوظة: `converters=18` (cold entry) / `converters=0` (warm entry) — لا توجد عينات أثناء التمرير.
- ❌ لم أُثبت ما إذا كانت تُعاد هندسة القطع أثناء التمرير (المنطق الساكن يشير إلى لا، لكن **القياس غير متاح**).

### 6.3 تجربة CornerRadius البديلة
❌ **لم تُجرَ.** لم أستبدل `Clip` بـ `Border.CornerRadius`، لأن التكافؤ البصري (قص الصورة، حدود الدائرة، عدم ظهور الزوايا، عدم التشويه، الحفاظ على الجودة) **لم يُثبت**. لم ألمس صور الإنتاج.

| `RenderBlurredWallpaper` (سطر 540) | يُستدعى داخل `new Thread(...)` مع `SetApartmentState(STA)` (الأسطر 535–571) — **خيط عامل مستقل، ليس UI Thread** |

### 7.2 الحكم
- ❌ **ادعاء التقرير السابق «RenderBlurredWallpaper/CopyPixels يجمّد خيط الواجهة» مُفند من حيث الخيط:** العمل الثقيل منقول إلى خيط STA عامل.
- ❌ **لم أجد أي مسار كود يربط إزاحة التمرير (ScrollOffset) بتحديث الزجاج.** التحديثات مرتبطة بتغيّر الحجم أو حركة الدرج (drawer) أو تحميل خلفية. لذلك **فرضية «تحديث الزجاج أثناء التمرير» غير مؤسسة**.
- ❌ لم أُثبت بالقياس عدد الاستدعاءات أثناء تمرير فعلي (لا توجد مخرجات SSCB/Glass محفوظة بهذا الخصوص).
- ❌ **لم أنفّذ A/B بتعليق مادة زجاجية بعينها أثناء التمرير** — لأن فرضية الحدوث نفسها لم تثبت. لم أُعطّل الزجاج أو الخلفيات في الإنتاج (وممنوع أصلاً).

## 12. الأسباب المثبتة مقابل الفرضيات

### 12.1 ما ثبت في هذه الجلسة (حقائق كود/تهيئة/قياس)

1. **أداة القياس السابقة معيبة:** CPU من `TotalProcessorTime` لكل العملية، بنافذة ~3.2–3.4s تشمل 2.2s سكون، بدقة 15.6ms، مع إسناد تبويب فاشل في 16/20 صفاً.
2. **أرقام الإطارات السابقة ليست إطارات معروضة:** مصدرها `CompositionTarget.Rendering`، وتوجد قيم >60Hz في السجلات المحفوظة.
3. **النافذة ليست Layered ولا بلا حدود:** `WS_EX_LAYERED=False`, `WindowStyle=SingleBorderWindow`, `AllowsTransparency` غير مضبوط.
4. **CircleClipConverter مخزّن ومجمد فعلاً:** لا تنشئ geometry غير مجمدة في كل استدعاء.
5. **عمل الـ Blur/CopyPixels خارج UI Thread:** خيط STA عامل + مسار خلفي.
6. **محفّزات الزجاج مرتبطة بالحجم/الدرج/تحميل الخلفية، لا بإزاحة التمرير** (فحص ساكن للمسارات).
7. **الملف التنفيذي المقاس أقدم من تعديلات Working Tree** → أرقام التقرير لا تمثل الكود الحالي.

### 12.2 ما لم يثبت — فرضيات مفتوحة (لا تُعامل كأسباب)

## 13. ترتيب الأسباب بحسب التأثير الفعلي

**لا يمكن ترتيب أسباب أداء بترتيب تأثيرها دون قياسات صالحة**، وأرفض استبدال ذلك بترتيب تخميني. ما أستطيع ترتيبه هو **درجة اليقين**:

1. عيوب منهجية في أداة القياس (يقين كامل — موثّق بالنص والكود).
2. وصف تركيب النافذة السابق خاطئ (يقين كامل — Win32 + XAML).
3. وصف CircleClipConverter السابق خاطئ (يقين كامل — الكود).
4. وصف خيط الـ Blur السابق خاطئ (يقين كامل — الكود).
5. تكلفة AncestorType / Glass / DWM أثناء التمرير (مجهولة — تحتاج A/B).

**ترتيب الاختبار المقترح بعد استعادة أدوات القياس:** PresentMon/ETW أولاً (لإثباتPresent Time)، ثم UI-thread CPU/Dispatcher، ثم AncestorType، ثم DWM Opaque A/B، ثم Converter، ثم Glass.

| المشكلة المُثبتة | أصغر تصحيح مقترح (أدوات فقط) |
| :--- | :--- |

| EXE أقدم من الكود | إعادة بناء من Working Tree الحالي قبل أي A/B |
